# ADR-0004: Rendering engine — single commonMain rewrite with C2a/C2b split

**Status:** Accepted. **Amended 2026-07-12 (ADR-0018 / owner C2):** Android production text/icon/**composition** may be **routed onto commonMain** `WatermarkCellComposer` / `composeOverBackground` under the gated schedule in [ADR-0018](0018-option-c2-common-raster-android-export.md). Prior addenda S4d-8 / S4d-17 / S4d-190 that forbade production routing **without** owner reopen are **superseded for that ban only**; byte-parity with legacy native is still **not** claimed. Historical S4d-* text below remains evidence. Original status body follows. ·  C2a (extraction) landed; the originally-bundled "C2b" was executed as the S3a–S3c-3 sub-slices — image-space sizing (S3a), `TextMeasurer` measurement (S3b), Compose `Canvas` preview swap (S3c-2), and `WaterMarkImageView`/`ViewInfo` retirement (S3c-3) are all **done**. For Desktop/iOS, commonMain `WatermarkCellComposer.composeOverBackground` is the accepted composition path. · **Amended 2026-06-28 (S4d-190, No-Go):** routing **Android** production composition onto `composeOverBackground` was assessed and **declined** — Android stays native on `WatermarkRenderer.compose` (parity unprovable read-only: `BitmapShader(REPEAT/CLAMP)`+`drawRect` vs a `drawImage` grid/decal loop, plus byte-vs-float alpha; preview is a live-canvas sub-region that does not map; low value since the cell raster stays native per S4d-8/S4d-17). Reopening needs an explicit owner decision starting with a **test-only Robolectric NATIVE FNV measurement** (compose both ways with the native cell `.asImageBitmap()`); no production routing without that gate. · **Amended 2026-06-18 (S4d-8, Option A):** the **icon** production draw-swap on Android is **NOT pursued** — Android icon rendering stays on the native `WatermarkRenderer.buildIconShader`/`Canvas.drawBitmap` path; commonMain `composeIconCell` is the **Desktop/iOS** icon renderer. See the addendum below. · **Amended 2026-06-28 (S4d-212, density thread CLOSED):** the suspected Android production-vs-debug watermark "2× density regression" / debug preview-export WYSIWYG bug is **withdrawn** — clean device measurement found debug export ≈ production export (1.06×) and debug preview ≈ debug export (0.91× same domain); S4d-210's 8.64% was a double-watermark/picker-recency artifact. The only real difference is a modest ~1.24× text-size drift (image-space `REF_WIDTH=1000` device-independent sizing vs legacy v2.10.0 device-dependent `1/MSCALE_X`). This warrants **no `REF_WIDTH` change, no golden rebaseline, and no renderer rewrite**; it only reinforces the standing position that **Android production raster/draw stays native while sizing constants/math stay shared** (text image-space sizing is already single-sourced through commonMain `WatermarkGeometry.REF_WIDTH`/`fontPx` for Android/Desktop/iOS — S4d-181/182). (Note: coverage is text-size-invariant at `hGap=vGap=0`; size deltas must be read from tile period — see `findings.md`.) · **Plan ref:** D4, C2a/C2b (C2b realized as S3a–S3c-3)

## Context
The engine's portable core is ~400–500 LOC and every drawing primitive maps ~1:1 to `androidx.compose.ui.graphics`/`ui.text` common APIs (StaticLayout→TextMeasurer, BitmapShader(REPEAT)→ImageShader(Repeated), offscreen Bitmap+Canvas→ImageBitmap+CanvasDrawScope). Two design debts: preview/export composition is duplicated, and export scale derives from the preview View's matrix (`1/MSCALE_X`, both axes — bug) via `ViewInfo`, which is window-size-dependent (a correctness bug on Desktop). *(Superseded — see Status: the composition was unified into `WatermarkRenderer.compose` (C2a) and the `1/MSCALE_X`/`ViewInfo` export-scale coupling was removed in S3a/S3c-3; export is now image-space. The corrected per-axis rule survives as the unwired `WatermarkGeometry.exportScale` target for resizable surfaces.)*

## Decision
Rewrite ONCE in commonMain-compatible compose-ui graphics; do NOT keep per-platform engines. Split:
- **C2a:** extract `WatermarkRenderer`; the existing View AND `generateImage` both delegate to it; zero behavior change; strict same-platform goldens gate the swap. Golden harness is built BEFORE C2a against the old engine (C1.7).
- **C2b (executed as S3a–S3c-3):** replace the AndroidView preview with a Compose `Canvas` (S3c-2); move to image-space watermark sizing (S3a — adopted **Option A**, reinterpreting persisted `textSize` in image-space at `REF_WIDTH=1000` with **no** DataStore migration write, instead of the originally-planned one-time config migration); delete `WaterMarkImageView`/`ViewInfo` (S3c-3). **Deviation from the original plan:** `WaterMarkShader` is **retained**, not deleted — it is the current return type of `WatermarkRenderer.build*Shader` and the `compose` parameter, used live by the preview, export, and goldens. It can be revisited if/when the commonMain composition rewrite replaces the Android `BitmapShader` wrapper.
Only decode/encode/EXIF-orientation/photo-store are expect/actual (behind interfaces, ADR-0005).

## Consequences
- Completing the Compose migration and creating the CMP engine become the same work.
- The sizing re-spec changes what persisted `textSize` means → product sign-off + config migration + golden re-baseline required at C2b (Risk R4).
- Headless TextMeasurer needs platform bootstrap (`createFontFamilyResolver(context)` on Android).
- **CJK measurement (ACCEPTED, S3b/D1):** the commonMain `TextMeasurer` seam is byte-exact vs legacy `StaticLayout` for the covered Latin/emoji/bold/italic rows, but **CJK cell height grows** (width stays exact) — a Compose line-height difference that scales with text size and line count (device-independent deltas, held on SM-S906E and emulator-5554 / API 36: single-line +1/+2/+5px at 12/24/48f; two-line +4/+9/+18px). **Accepted** the Compose CJK line-height as the renderer baseline (Risk R4 re-baseline), not fragile per-script compat tuning. **Wired in S3b:** `WatermarkRenderer.buildTextShader` measures the text-cell box via the `TextMeasureEnv`/`WatermarkTextMeasurer` seam for both preview and export; **drawing stays legacy `StaticLayout`** (S3b is measurement-only). Gated by `WatermarkCellParityGateTest` (ADR-0010/0014); the two CJK S0 export-golden entries were re-baselined, non-CJK unchanged. Under the updated device policy the gate's device-pinned absolutes were re-pinned to the S3b acceptance target emulator-5554/API 36.

## Addendum — icon draw-swap: Android stays native (S4d-6 → S4d-8, Option A, 2026-06-18)

The plan above implies the **composition/raster** will eventually move into a commonMain renderer for every platform. For the **icon** cell this was attempted and is **deliberately not done on Android**:

- **S4d-6** wired Android `WatermarkRenderer.buildIconShader` to delegate the offscreen icon cell to commonMain `WatermarkCellComposer.composeIconCell`. It is byte-identical for solid/axis-aligned icons, but the strict export golden `WatermarkExportGoldenTest.icon_rot_315` (a **non-uniform** icon at **315° — the production default rotation**) failed by 16/1936 colour pixels → blocked (no rebaseline).
- **S4d-7** fixed `composeIconCell` to use Android's **float** pivot + **float** top-left placement (point-draw). This was the right fix for *placement* and reduced the delta 16→5 px, but could not reach byte-exact: **no commonMain `drawImage` overload offers float-placement AND nearest-filter together** (the `dstSize` overload is nearest but rect-maps with a half-texel offset; the `topLeft` overload places correctly but has no `filterQuality`, so it bilinear-samples the rotation). The only API with both is the platform `nativeCanvas.drawBitmap`, which is **not** commonMain. So commonMain Compose graphics **cannot reproduce `android.graphics.Canvas.drawBitmap` byte-for-byte for rotated non-uniform icons**.
- **S4d-8 (this decision, Option A):** **Android icon production/export stays on the native `WatermarkRenderer.buildIconShader` raster** (already strict-golden-protected). The commonMain `composeIconCell` (with the S4d-7 float-placement improvement, which is strictly more correct) is retained as the **Desktop/iOS** icon renderer, where there is no `android.Canvas` oracle to byte-match. The portable, shared win is the **geometry** (`WatermarkGeometry`, already driving Android cell sizing), not a byte-identical Android raster.

**Durable rule (do not re-litigate without an owner decision):** do NOT re-attempt byte-exact Android icon parity through commonMain Compose. Changing this requires an explicit owner choice of either (B) a tolerance/perceptual icon golden policy, or (C) a commonMain nearest-neighbour rotated blitter — neither of which is in scope by default. Text follows the same caution: its commonMain raster (`composeTextCell`) is also Desktop/iOS-first and gated behind the bundled-font + on-device work, not an Android draw-swap.

## Addendum — Desktop text renderer realized (S4d-18, 2026-06-18)
The "Desktop/iOS-first" plan for the commonMain text raster is now partly executed: `shared/src/desktopMain/.../DesktopWatermarkTextRenderer.kt` renders watermark **text** on Desktop through the shared `WatermarkCellComposer.composeTextCell` + the bundled Latin+CJK font (desktop Skiko `createFontFamilyResolver()`, byte-`Font` factory, fonts in `desktopMain/resources/fonts/`, **no compose-resources**). `:desktopApp:run` produces real PNGs (Latin/CJK/multiline/rotated); `DesktopTextRendererGoldenTest` is the Desktop perceptual gate. The Skiko runtime (`compose.desktop.currentOs`) is a **desktop-target-only** `desktopMain` dependency and does not reach `:app` (verified 0 skiko in `:app:debugRuntimeClasspath`). Android text/icon production stays native (S4d-8 icon Option A + S4d-17 text Option C). The shared win remains the geometry + the platform-injected `TextRasterEnv` boundary; iOS reuses the same boundary next (S4d-20/C5).

## Addendum — Desktop composition realized (S4d-19, 2026-06-18)
The composition step (the part of the engine that was still Android-only `WatermarkRenderer.compose`) now has a platform-neutral commonMain primitive: `WatermarkCellComposer.composeOverBackground(background, cell, tileMode, offsetX, offsetY, alpha)`. REPEAT grid-tiles the already-rendered cell from the origin across an already-decoded background `ImageBitmap`; CLAMP draws one decal at a fractional offset — mirroring `compose`'s REPEAT/CLAMP branches and reusing the commonMain `WatermarkTileMode` enum. It supports **REPEAT/CLAMP only** and throws for the legacy non-product `MIRROR`/`DECAL` ids (their `BitmapShader` sampling is not reproduced by the draw loop — no parity claimed; a separate gate if ever needed). Decode/encode and background acquisition stay a per-platform boundary: desktopMain `DesktopWatermarkComposer` generates a deterministic asset-free sample background and AWT-encodes PNG; `:desktopApp:run` writes `build/s4d19-desktop-watermark/{repeat,clamp}_watermark.png`. Gated by `DesktopWatermarkCompositionGoldenTest` (dims, tiled-vs-localized, determinism, PNG). **Still NOT wired into Android production** — Android composition stays native (`WatermarkRenderer.compose`); this is the Desktop/iOS path. **Routing Android production composition onto `composeOverBackground` was assessed and declined (S4d-190, No-Go)** — Android stays native on `WatermarkRenderer.compose`; reopening requires an explicit owner decision plus a **test-only Robolectric NATIVE FNV measurement** before any production routing.

## Addendum — Desktop real-image decode boundary (S4d-20A, 2026-06-19)
The Desktop pipeline now consumes a **real `ImageIO`-decoded** image, not only a generated background. desktopMain `DesktopImageDecoder.decode(bytes|file)` reads via AWT `ImageIO.read` and bridges `BufferedImage.toComposeImageBitmap()`; `DesktopWatermarkComposer.composeOverRealImage(imageBytes, …)` chains decode → `DesktopWatermarkTextRenderer.renderTextCell` → `WatermarkCellComposer.composeOverBackground` → AWT PNG encode. This makes the ADR-0004 **decode boundary** concrete on Desktop while keeping commonMain decode-free (already-decoded `ImageBitmap` in, composed out) — no commonMain decode API was added. No new dependency (`javax.imageio` is JDK; `toComposeImageBitmap()` is the desktop-target-only `compose.desktop.currentOs` from S4d-18), so `:app`/shared-android runtime classpaths stay skiko-clean. Android decode stays native (`BitmapFactory` in `:app`); the iOS decoder (`UIImage`/`ImageIO`) is the next slice, reusing the same commonMain composition. Gated by `DesktopRealImageDecodeGoldenTest` (decode dims, output differs-from-input via re-decoded pixel evidence, determinism, valid PNG, undecodable-bytes throws).

## Addendum — iOS renderer boundaries landed (S4d-20B, 2026-06-19)
The "Desktop/iOS-first" plan reaches iOS: `shared/src/iosMain` now has the iOS platform boundaries mirroring desktop — `IosImageDecoder` (Skia `org.jetbrains.skia.Image.makeFromEncoded` → `toComposeImageBitmap()`), `IosTextRasterEnv` (skiko `createFontFamilyResolver()` + a byte-`Font` `bundledFontFamily(latinBytes, cjkBytes, latinFirst)`), and `IosWatermarkRenderer` (text: `renderTextCell` + `composeOverImage` decode→cell→`composeOverBackground` + Skia PNG encode). iOS is a Skiko backend, so the accepted commonMain primitives run unchanged and **no commonMain decode API is added** (decoded `ImageBitmap` in, composed out). **No new dependency** — Skia is part of the Compose-Multiplatform iOS klibs already on `:shared`; `:app`/shared-android runtime classpaths stay free of skiko/ios. iOS **font bytes** are a caller responsibility: Kotlin/Native has no JVM-classpath `getResourceAsStream` and compose-resources is excluded (CMP-9547), so `bundledFontFamily` takes `ByteArray`s; a real iOS app supplies them from `NSBundle`/`NSData` (C5). **Proof level:** both iOS targets compile and both iOS test executables LINK to native `.kexe` (`linkDebugTestIosSimulatorArm64`/`linkDebugTestIosArm64`). **Update — S4d-55 (2026-06-26):** the `iosSimulatorArm64Test` RUN is no longer deferred — it RAN on the now-installed iOS 27.0 simulator and passed 41/41 (incl. `IosWatermarkRendererTest`), and the `iosApp` built/launched executing shared code live. **S4d-58 (2026-06-26):** the iOS app **render + export UI** is runtime-proven via a `#if DEBUG`/`-uiTestFixtureImage` XCUITest seam (fixture image → real `IosWatermarkRenderBridge` → watermarked preview → Save to Photos → Share, 2/0); only real PHPicker grid-cell *selection* stays unproven (beta-toolchain/system-UI limit, S4d-57). **Update — S4d-115 (2026-06-27):** iOS now also has the Kotlin-only **icon** render foundation: `renderIconCell` wraps commonMain `composeIconCell`, and `composeIconOverImage` decodes background+icon bytes via `IosImageDecoder` before composing through `composeOverBackground`; icon cells are rendered opaque and watermark alpha is applied once at composition. This remains the Desktop/iOS perceptual icon path, **not** Android native `Canvas.drawBitmap` byte parity, and Android decode/render stays native.

**Update — S4d-116 (2026-06-27):** iOS icon bytes are now persisted outside the renderer as app-private `NSDocumentDirectory/watermark_icons/icon_<NSUUID>` files and referenced by `MediaRef(path)`. Ownership-checked cleanup keeps this an iOS storage edge, not a commonMain decode API.

**Update — S4d-117 (2026-06-27):** iOS `WatermarkWorkflow` now chooses Text vs Image at render time. Image mode reads persisted icon bytes through the iOS config bridge and calls `IosWatermarkRenderBridge.renderIconWatermarkedPng`, a Swift-catchable wrapper over the accepted `composeIconOverImage` path; missing/unreadable icon becomes a visible failure, not a text fallback. Picker UI remains separate.

**Update — S4d-118 (2026-06-27):** iOS has the minimal UI to reach Image mode: a separate SwiftUI icon `PhotosPicker` loads picked bytes and calls the existing `setIconFromBytes` bridge, then re-renders through the S4d-117 Image branch. Swift stores only a transient thumbnail and never parses the persisted icon path. This completes the iOS image-watermark functional path; it is not a 1:1 Android parity claim.

## Addendum — Desktop EXIF orientation at the decode edge (S4d-21, 2026-06-19)
`DesktopImageDecoder` now bakes JPEG **EXIF orientation** into the decoded `ImageBitmap` before bridging to Compose, matching the Android product decode policy (Android bakes EXIF rotation via `androidx.exifinterface`/`BitmapUtils`). A tiny **pure-JDK** reader (`parseExifOrientation`) scans the JPEG APP1 `Exif\0\0` segment and reads TIFF IFD0 tag 0x0112 (II/MM byte order; best-effort, returns 1 for non-JPEG/missing/malformed), and `applyExifOrientation` applies the matching rotation/flip via AWT `AffineTransformOp` (NEAREST, lossless for 90°-multiples) for all 8 orientations (5–8 swap width/height). This keeps orientation a **platform decode-edge** concern: commonMain stays decode-free (`composeOverBackground` still takes an already-decoded `ImageBitmap`), and `DesktopWatermarkComposer.composeOverRealImage` now receives an upright, orientation-correct image. **No new dependency** — `ImageIO`'s JPEG plugin doesn't surface EXIF orientation, but the APP1/TIFF tag is parsed locally, avoiding `metadata-extractor`/`commons-imaging`; the `androidx.exifinterface` on `:app`'s classpath is the pre-existing Android lib, untouched. Gated by `DesktopExifOrientationTest` (deterministic generated JPEG+EXIF fixtures, no binary asset; asserts 1/3/6/8 corner+dims). Android decode stays native; the iOS decoder can adopt the same orientation step later.
